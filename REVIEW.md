# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Grace period logic strictly > 10:00 failure. Starter truncates to minutes first (`int(seconds / 60)`), then tests `minutes > 10`. At 09:40:01 (601s), `int(601/60) = 10`, so `10 > 10` is False, returning 0. Rule R2 states strictly > 10:00 is late (09:40:01 must return 10). | Input punch_in at 09:40:01 for shift 09:30. Starter returns 0 instead of 10. | Compare elapsed seconds directly: `diff_seconds > 600`. When True, calculate `diff_seconds // 60`. Truncate instant to whole seconds first per R1. |
| 2 | `compute_late_minutes` (lines 33–37) | Naive timezone mismatch when replacing hours on `punch_in`. Replacing `hour` and `minute` with IST shift times directly on a UTC or naive datetime causes incorrect comparisons (e.g., 04:00 UTC vs 09:30 UTC produces negative duration). | Punching in at 09:45 IST (04:15 UTC). `punch_in.replace(hour=9, minute=30)` treats it as 09:30 UTC, producing -5 hours difference. | Convert `punch_in` to IST timezone before constructing IST `shift_start_dt`, or construct `shift_start_dt` with `tzinfo=IST` and compare aware datetimes. |
| 3 | `compute_work_hours` (lines 40–42) | Uses Python's built-in `round()`, which performs banker's rounding (round half to even) rather than round half-up. Rule R4 explicitly demands round half-up. | `compute_work_hours` on 2.675 hours produces 2.67 instead of 2.68. | Used `decimal.Decimal` with `ROUND_HALF_UP` on total elapsed seconds divided by 3600. |
| 4 | `compute_overtime` (lines 44–48) | Missing 30-minute threshold. Starter returns `max(0, int(...))` for any positive minutes, ignoring Rule R3 ("counted only if that is at least 30; otherwise 0"). | Punch-out 5 minutes after shift end (e.g., 18:35 for 18:30 shift) returns 5 instead of 0. | Added condition: if overtime minutes < 30, return 0; otherwise return the whole minutes. |
| 5 | `compute_overtime` (lines 44–48) | Overnight shift handling for shift end date. For shifts crossing midnight (e.g., 22:00 - 06:00), shift end falls on the next calendar day (`date + 1 day`). Starter builds `end` using `date_str` directly, comparing against the previous day's morning (~24h extra overtime). | Overnight shift record ending at 06:40 IST calculates ~1480 overtime minutes instead of 40. | Check if shift is overnight (`shift_end <= shift_start`). If so, add one day to attendance date when constructing `shift_end_dt`. |
| 6 | `health` (lines 72–74) | Returns HTTP 200 without checking MongoDB connectivity. The contract requires returning 200 only if MongoDB answers a ping, otherwise 503. | Stop MongoDB service; calling `GET /health` still returns `{"status": "ok"}` with HTTP 200. | Added `client.admin.command('ping')` inside a `try/except` block, raising `HTTPException(503, "Database unavailable")` on failure. |
| 7 | `create_employee` (lines 77–85) | Race condition in employee creation (check-then-insert) and missing unique index enforcement. Concurrent requests with identical `emp_code` can both pass `find_one` check. | Sending two simultaneous POST `/employees` requests with identical `emp_code` results in duplicate documents or unhandled DB errors. | Created a unique index on `emp_code` at startup and caught `pymongo.errors.DuplicateKeyError` to reliably return 409 Conflict. |
| 8 | `create_employee` (lines 77–85) | Missing schema validations required by OpenAPI: `emp_code` format (`^EMP\d{4,6}$`), email regex, string lengths, and checking that `shift_start != shift_end`. | POST with `emp_code: "invalid"`, or `shift_start: "09:30", shift_end: "09:30"` returns 201 instead of 422. | Added Pydantic field constraints, regex patterns, and a model validator ensuring `shift_start != shift_end`. |
| 9 | `create_employee` (lines 77–85) | `created_at` response serialization. Starter sets `doc["created_at"] = datetime.now()`, returning ISO string or datetime object instead of integer epoch milliseconds per OpenAPI schema `EpochMillis`. | `created_at` in JSON response is a string like `"2026-10-13T10:00:00"` instead of an integer epoch timestamp like `1791885600000`. | Stored UTC `datetime` in MongoDB and serialized to integer epoch milliseconds in API responses. |
| 10 | `list_employees` (lines 88–96) | Off-by-one error in pagination `skip`. Starter does `skip = page * page_size`. Since `page` is 1-indexed (starts at 1), page 1 skips the first 20 records. | Requesting `GET /employees?page=1&page_size=20` returns items 21–40, skipping the first 20 employees. | Fixed calculation to `skip = (page - 1) * page_size`. Also added query parameter validation (`page >= 1`, `1 <= page_size <= 100`). |
| 11 | `list_employees` (lines 88–96) | `total` counts entire collection rather than filtered query. Starter does `total = db.employees.count_documents({})`. Contract states: "`total` counts the filtered set, not the whole collection." | Querying `GET /employees?department=Sales` returns `total` equal to all employees in the company instead of Sales employees. | Changed to `total = db.employees.count_documents(q)`. Also added sort by `emp_code` ascending per contract. |
| 12 | `punch_in` (lines 99–121) | Unhandled 500 error when employee does not exist. Starter does `emp = db.employees.find_one(...)` without checking `None`; `emp["shift_start"]` raises `TypeError` (HTTP 500). | POST `/attendance/punch-in` with non-existent `emp_code: "EMP9999"` returns 500 Internal Server Error instead of 404. | Check `if not emp: raise HTTPException(404, "Employee not found")`. |
| 13 | `punch_in` (lines 99–121) | Check-then-insert race condition on duplicate punch-ins. Two concurrent punch-in requests for the same date both pass `find_one` and insert duplicate attendance records. | Two concurrent punch-in requests both return 201 Created and create two documents for the same employee and date. | Created a compound unique index on `(emp_code, date)` at startup and caught `DuplicateKeyError` to return 409 Conflict. |
| 14 | `punch_in` (lines 99–121) | Rule R1 overnight shift date determination. Starter uses `d = ts.date().isoformat()`. If an overnight employee punches in in the early morning before `shift_end`, the punch belongs to the previous day's shift. | Overnight employee (22:00–06:00) punching in at 05:30 IST is assigned current date instead of previous day's date. | Implemented Rule R1: if shift is overnight and IST punch time < `shift_end`, assign attendance date to previous calendar day. |
| 15 | `punch_in` (lines 99–121) | Internal MongoDB `_id` exposed as `id`. Starter sets `doc["id"] = str(res.inserted_id)`. The contract states: "Attendance records have no id either; a record is addressed by (emp_code, date). _id is internal and never appears." | Response contains `"id": "670..."`. | Removed `"id"` injection and stripped `_id`. Formatted all timestamps as integer epoch milliseconds. |
| 16 | `punch_in` (lines 99–121) | Missing status validation. Accepts any arbitrary string in `status` instead of restricting to `PRESENT`, `WFH`, `ON_DUTY` per OpenAPI contract. | POST with `status: "INVALID"` or `status: "ABSENT"` is accepted with 201. | Restricted status in `PunchInRequest` to enum `PresenceStatus` (`PRESENT`, `WFH`, `ON_DUTY`), returning 422 on invalid status. |
| 17 | `list_attendance` (lines 124–150) | In-memory loading and sorting across the entire collection. Starter calls `list(db.attendance_logs.find(q))` and sorts in Python, causing severe performance degradation and OOM on ~100k documents. | On large datasets, `GET /attendance` takes seconds or runs out of memory. | Replaced in-memory sorting and slicing with indexed MongoDB cursor operations: `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`. |
| 18 | `list_attendance` (lines 124–150) | Secondary sort order missing. Starter sorts only by `date` descending. Contract requires: "Sorted by date descending, then emp_code ascending." | Records on the same date appear in arbitrary order. | Applied compound sort `[("date", -1), ("emp_code", 1)]` backed by a matching compound index. |
| 19 | `list_attendance` (lines 124–150) | Missing date range validation. Contract specifies that `date_from > date_to` must return HTTP 422. Starter returns empty list with 200. | Query `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` returns 200 instead of 422. | Added validation raising `HTTPException(422, "date_from cannot be greater than date_to")`. |
| 20 | Database setup / Lifespan | No indexes created at startup. Starter never creates indexes, causing queries and explain checks to fail on large collections. | Startup does not ensure indexes; `/admin/explain` would show collection scans. | Added startup lifespan event creating all unique and compound indexes idempotently (`emp_code`, `(emp_code, date)`, `(date, -1, emp_code, 1)`, etc.). |
| 21 | PyMongo Client | `tz_aware=True` not configured on `MongoClient`. PyMongo returns offset-naive datetimes by default, causing timezone confusion. | Mixing naive and aware datetimes when computing time differences raises runtime `TypeError`. | Configured `MongoClient(..., tz_aware=True)` and normalized boundary conversions to UTC / IST explicitly. |

### Things examined and decided were NOT defects
1. **Addressing attendance records by `(emp_code, date)` without a synthetic ID**: `DATA_MODEL.md` explicitly specifies that attendance records have no public ID and are natural-key addressed by `(emp_code, date)`.
2. **Calendar dates stored as plain strings (`YYYY-MM-DD`)**: Per `DATA_MODEL.md` section 1, calendar dates and times of day (`HH:MM`) are stored as strings on purpose so they do not force an arbitrary UTC instant conversion.
3. **Punch-in and punch-out not appending to `history`**: Per `DATA_MODEL.md` section 4, `history` is specifically reserved for manual corrections (`PATCH`). Regular punches are original events and must never write to `history`.
